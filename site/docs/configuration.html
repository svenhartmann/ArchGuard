Configuration & rules

Define source scope and architecture intent without hiding the evidence.

Configuration precedence

  1. An explicitly supplied --config file.
  2. .archguard/archguard.toml under the analyzed project root.
  3. Legacy archguard.toml at the project root.
  4. Derived values and defaults where no file or section is supplied.

Relative source roots are resolved against the project root. Invalid configuration fails source analysis instead of silently resetting it. Service inventory reads discovery exclusions independently and reports configuration-reading gaps in its diagnostics.

A small source-scope example

[project]
source_roots = ["src"]
languages = ["ts", "js"]
exclude = ["**/node_modules/**", "**/dist/**", "**/generated/**", "**/*.spec.*"]

[modules]
depth = 2

[rules]
deny_cycles = "module"
max_scc_size = 1

Adjust languages and source roots to the actual project. languages = ["auto"] enables automatic language selection. An explicit exclude list replaces that field's defaults; retain the patterns you still need. The module depth changes the aggregation boundary used for package analysis.

Declare a dependency boundary

[[dependency_rules]]
name = "ui-no-persistence"
from = ["ui/**"]
to = ["persistence/**"]
severity = "error"
message = "UI must call the application API."

Match the module paths that ArchGuard actually reports. A directory named src/ui may appear as ui when src is the source root. Inspect the graph or effective configuration before writing patterns.

Declared and derived layers

[[layers]]
name = "domain"
contains = ["domain/**"]
may_depend_on = []

[[layers]]
name = "application"
contains = ["application/**"]
may_depend_on = ["domain"]

These are example boundaries, not a recommendation for every codebase. Declared rules express intent and can fail the check. Inferred layer rankings are observations, not a substitute for your architecture policy. A module outside the declared patterns may remain unranked.

Inspect what is actually applied

archguard --config /path/to/archguard.toml config /path/to/project --format json
archguard --config /path/to/archguard.toml check /path/to/project

The effective configuration reports provenance by section. Use it to resolve unexpected exclusions, source roots or derived settings rather than repeatedly changing the displayed view.

Adopt a baseline deliberately

archguard baseline write .
archguard check . --baseline
archguard baseline diff .

Writing a baseline records the current cycle identities in .archguard/baseline.json. It is an explicit decision to accept that starting point. With a baseline, existing cycle identities can be tolerated while new ones fail; other enabled gates still apply. Review the file in version control instead of regenerating it on every CI run.

Keep intentional project data

.archguard/ contains both disposable output and intentional inputs. Configuration, baselines, scenarios and imported measurements may belong in version control. Caches and regenerated reports usually do not. Avoid ignoring or deleting the whole directory without deciding which evidence your team needs to retain.
