ARCHGUARD HANDBOOK

Refactoring and load simulation

Compare architecture changes and capacity assumptions before changing a system.

Try a virtual refactoring

Start with the dependency graph. In the desktop, open Graph, enable Manual simulation, propose a cut or move, and apply it in the operations strip. Compare cycle groups and ACD, then Undo, Clear or Export.

archguard cycles .
archguard suggest . --cycle scc-1 --max 3
archguard simulate . --cut "actual.source,actual.target"
archguard simulate . --ops archguard-simops.json --format json

Use actual cycle IDs and node names from your analysis. CLI operations include --cut FROM,TO, --move NODE:PARENT and --merge SURVIVOR,ABSORBED. Exported operation files are inputs to --ops.

The operation changes the graph model, not your source files. Quality, security and source findings still describe the actual code. A suggested single-edge cut is a proposal to investigate, not an automatic implementation plan.

Keep a named experiment

The desktop Scenarios control saves experiments under .archguard/scenarios/. Loading, overwriting and deleting prompt for confirmation. Export operations for CLI use; do not assume every saved scenario document is an operations file.

Create a load scenario

The load model is implemented in source branch sim/load-scenarios-next, revision b46949a2. It is separate from the integrated source snapshot used by the other guides. Check archguard load --help in your build.

List services first, then choose an actual entry service ID or unique name. The following frontend is a placeholder:

archguard services . --format json
archguard load . --template --entry frontend > load.json
archguard load . --scenario load.json
archguard load . --scenario load.json --format json

Edit the generated template before evaluation. Set entry rates and service assumptions such as instances and service time. Repeat --entry for multiple entries. A template with no entries produces zero rates and explicitly reports that fact.

Record where estimates come from

The schema is archguard-load-scenario/v1. A rate estimate such as entries[0].requests_per_second has the shape below. Use measured provenance only when a measurement supports it.

{"value": 40.0, "provenance": "assumed"}

Unknown calls per request remain a 0–1 range. Results propagate ranges and name their drivers: entry rate, upstream calls, self-time, instances and CPU assumptions. Concurrency candidates and contract payload shapes provide evidence to investigate; they do not silently become numeric capacity or request-size inputs.

Use the reproducible alternative solver

Add this top-level property to the generated scenario:

"simulation": {"arrivals": 2000, "seed": 3}

The seeded simulation models Poisson arrivals and exponential service times at both bounds. Other parts of the model remain analytic. Retries, timeouts and bursts are not modeled. No traffic is sent to your services: results describe the given assumptions, not a measured benchmark.
