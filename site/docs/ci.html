CI & quality gates

Use repeatable checks, deliberate baselines and inspectable reports.

On this pageStart with a direct checkBaseline an existing codebaseKeep the report when the gate failsCompare changes and document driftDependency security evidenceA practical rollout

Start with a direct check

Install a pinned ArchGuard build in your CI environment, check out the project, and run:

archguard check .

Keep the source revision, configuration and required language tools consistent between local and CI runs. A report can have partial compiler evidence even when import analysis succeeds.

Exit codeMeaningWhat to do
0Command or gate succeeded.Read coverage notes; success is not proof of complete runtime analysis.
1Findings crossed a gate, or a comparison/check reported a difference.Review the reported cycles, rules, thresholds or document drift.
2Usage error.Check arguments and command-specific formats.
3Analysis, configuration or I/O failure.Fix the reported environment or input problem.

Baseline an existing codebase

archguard baseline write .
archguard check . --baseline

Create and review the baseline as a one-time adoption step, then commit it alongside the intended configuration. CI should read it. Regenerating it before every check would accept new cycles instead of detecting them.

Keep the report when the gate fails

For a POSIX shell, preserve the command's exit status while saving structured output:

set +e
archguard check . --format json > archguard-check.json
status=$?
set -e
# Publish archguard-check.json with your CI artifact step, even on failure.
exit "$status"

This snippet does not upload anything itself. Configure your CI's artifact step to run even after a failed gate. Use --format sarif with check when your review system accepts SARIF; saving a SARIF file is distinct from uploading it.

Compare changes and document drift

archguard review . --base main --format html
archguard doc . --arc42 --check

Fetch the Git revision used by --base; shallow checkouts can omit it. The documentation check is read-only and returns 1 when the selected document is missing or outdated. Generate and review the document locally before enabling that gate.

Dependency security evidence

archguard security . --fail-on-found
archguard security . --cached --format json

The first command runs the supported Trivy integration and can require network access and an available advisory database. The second reads saved results without invoking the scanner. Cached results are not necessarily current; inspect their status and revision.

The ArchGuard repository's own release workflows additionally build native binaries, run smoke tests and scan release archives. Those release-pipeline checks do not automatically become checks for every project you analyze.

A practical rollout

  1. Agree on the source scope and language-tool setup.
  2. Run checks in reporting mode and review representative findings.
  3. Declare the architecture boundaries the team actually owns.
  4. Adopt a reviewed baseline if needed.
  5. Enable gates and retain enough evidence to explain failures.
  6. Review scope or tool changes before interpreting metric trends.
