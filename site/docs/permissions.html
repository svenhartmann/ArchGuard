ARCHGUARD HANDBOOK

Roles and permissions

Compare declared access across screens and endpoints, and turn explicit conventions into checks.

Separate declaration from evaluation

A declaration can be protected, explicitly open or undeclared. Evaluation for a particular user is allowed, denied or unknown. Missing or unreadable rules stay unknown. Navigation adds another question: whether a known path reaches that screen.

Choose anonymous access or actual roles from archguard ui-flow roles .. Multiple roles form the simulated assignment; a signed-in user without roles is distinct from anonymous access.

Read and export the permission matrix

archguard ui-flow matrix .
archguard ui-flow matrix . --kind screens --format csv
archguard ui-flow matrix . --kind endpoints --format json

Rows are screens and/or endpoints. Columns include anonymous, signed-in and catalog roles. A screen cell evaluates its own access declaration, not the entire navigation path. Permission IDs are not automatically separate columns. Use the Screens view for path conditions and frontend/backend mismatches.

Map guards and a separate backend

Use one [views] table in .archguard/archguard.toml, combining existing settings as needed:

[views]
backends = ["../backend"]
conventions = ["endpoint_access_declared", "frontend_backend_agree"]

[views.access]
mustBeAuthenticatedGuard = "authenticated"
hasRole = "role:$arg"
ApiPermission = "policy:$arg|authenticated"

Use names actually present in your application. $arg reads a literal argument; the suffix is a fallback when no argument exists. Arbitrary guard code is not executed. Additional repositories supply endpoint evidence and keep their own access configuration. CLI follows explicitly configured paths; MCP requires them inside its server root and refuses symlink traversal.

Introduce conventions gradually

Other checks include navigation_literal, http_url_literal, state_changes_in_entity, events_through_raise_function, navigation_resolves and endpoint_called.

archguard check .
archguard baseline write .
archguard check . --baseline

First inspect findings. Write a baseline only when you deliberately accept existing findings. Checks that lack enough route or call evidence report not evaluated. An endpoint without a recognized UI caller may serve an external client; it is not automatically unused.

Record a review decision

archguard review-decision record \
  --finding "<finding-id>" \
  --decision fix \
  --note "Declare the endpoint access explicitly."

Replace the ID with a real finding. Decisions are fix, accept-risk and defer. Valid acceptance affects the gate; expired acceptance no longer suppresses failure. Keep a reason that another reviewer can assess.

Query through MCP

Use ui_flow with {"view":"matrix","kind":"endpoints"}, or {"roles":["Admin"]}. Anonymous access uses {"anonymous":true}. Follow next_offset and carry the returned revision as expected_revision. See MCP setup.
