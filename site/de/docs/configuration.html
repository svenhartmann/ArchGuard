Konfiguration und Regeln

Definiere den Quellumfang und die beabsichtigte Architektur, ohne Belege auszublenden.

Rangfolge der Konfiguration

  1. Eine ausdrücklich über --config angegebene Datei.
  2. .archguard/archguard.toml unter dem analysierten Projektstamm.
  3. Die ältere archguard.toml im Projektstamm.
  4. Abgeleitete Werte und Standardwerte, wenn keine Datei oder kein Abschnitt angegeben ist.

Relative Quellverzeichnisse werden gegen den Projektstamm aufgelöst. Ungültige Konfiguration lässt die Quellanalyse fehlschlagen, statt sie stillschweigend zurückzusetzen. Das Service-Inventar liest Ausschlüsse für die Erkennung unabhängig und meldet Probleme beim Lesen der Konfiguration in seinen Diagnosen.

Ein kleines Beispiel für den Quellumfang

[project]
source_roots = ["src"]
languages = ["ts", "js"]
exclude = ["**/node_modules/**", "**/dist/**", "**/generated/**", "**/*.spec.*"]

[modules]
depth = 2

[rules]
deny_cycles = "module"
max_scc_size = 1

Passe Sprachen und Quellverzeichnisse an das tatsächliche Projekt an. languages = ["auto"] aktiviert die automatische Sprachauswahl. Eine ausdrückliche Ausschlussliste ersetzt die Standardwerte dieses Feldes; behalte die weiterhin benötigten Muster. Die Modultiefe verändert die Aggregationsgrenze der Paketanalyse.

Eine Abhängigkeitsgrenze deklarieren

[[dependency_rules]]
name = "ui-no-persistence"
from = ["ui/**"]
to = ["persistence/**"]
severity = "error"
message = "UI must call the application API."

Verwende die Modulpfade, die ArchGuard tatsächlich meldet. Ein Verzeichnis src/ui kann als ui erscheinen, wenn src das Quellverzeichnis ist. Prüfe Graph oder wirksame Konfiguration, bevor du Muster formulierst.

Deklarierte und abgeleitete Schichten

[[layers]]
name = "domain"
contains = ["domain/**"]
may_depend_on = []

[[layers]]
name = "application"
contains = ["application/**"]
may_depend_on = ["domain"]

Das sind Beispielgrenzen, keine Empfehlung für jede Codebasis. Deklarierte Regeln drücken eine Absicht aus und können die Prüfung fehlschlagen lassen. Abgeleitete Schichtrangfolgen sind Beobachtungen und ersetzen keine Architekturregeln. Ein Modul außerhalb der deklarierten Muster kann ohne Rangzuordnung bleiben.

Die tatsächlich angewendete Konfiguration prüfen

archguard --config /path/to/archguard.toml config /path/to/project --format json
archguard --config /path/to/archguard.toml check /path/to/project

Die wirksame Konfiguration meldet die Herkunft pro Abschnitt. Nutze sie, um unerwartete Ausschlüsse, Quellverzeichnisse oder abgeleitete Einstellungen zu klären, statt wiederholt die angezeigte Ansicht zu ändern.

Eine Baseline bewusst übernehmen

archguard baseline write .
archguard check . --baseline
archguard baseline diff .

Das Schreiben einer Baseline hält die aktuellen Zyklusidentitäten in .archguard/baseline.json fest. Damit entscheidest du ausdrücklich, diesen Ausgangspunkt zu akzeptieren. Mit einer Baseline können bestehende Zyklusidentitäten toleriert werden, während neue fehlschlagen; andere aktivierte Gates gelten weiterhin. Prüfe die Datei in der Versionsverwaltung, statt sie bei jedem CI-Lauf neu zu erzeugen.

Bewusst gepflegte Projektdaten erhalten

.archguard/ enthält sowohl ersetzbare Ausgaben als auch bewusst gepflegte Eingaben. Konfiguration, Baselines, Szenarien und importierte Messungen können in die Versionsverwaltung gehören. Caches und erneut erzeugbare Berichte normalerweise nicht. Ignoriere oder lösche nicht das gesamte Verzeichnis, ohne zu entscheiden, welche Belege dein Team erhalten muss.
