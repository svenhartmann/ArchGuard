UNDERSTANDING EVIDENCE

Missing evidence is not a zero.

A missing measurement can mean several things: a tool is unavailable, a reference is unresolved, or an execution was never recorded. None of these means “no problem”.

First ask: what do we know?

Imagine two classes. The first was analysed and no relevant calls were found. The second lacks required references. If both receive a zero, a measurement becomes indistinguishable from a gap. A ranking could make the class we know least about look reassuring.

ArchGuard keeps missing and unresolved evidence visible. The language guide explains which information comes from syntax, compiler analysis or additional inputs. Before comparing results, keep the version, source scope, exclusions and tools consistent.

One connection, different kinds of evidence

In the included Service Shop example, Compose describes configured HTTP relationships and startup dependencies. These answer different questions. A depends_on relationship is not an observed business call; a configured URL does not prove that every request takes that path.

Imported OpenTelemetry traces add recorded executions. But a missing span can reflect sampling or missing instrumentation. “Not seen in this recording” therefore does not imply “cannot happen”. The reproducible Service Shop walkthrough makes the distinction tangible.

Turn a view into a checkable statement

From the ArchGuard repository, run the static service analysis. No containers need to be started:

archguard services examples/service-shop --format json

Choose a connection and record its source path, relationship type and analysis scope. Then inspect the same location in the desktop app. The claim should be precise enough for another person to reproduce at the same commit.

A useful review includes its gaps

Ask a coding agent for a finding's source location and evidence type. Have it name unresolved targets and follow paginated responses before claiming completeness. A simulation then describes a possible graph change; tests and domain decisions remain part of the actual refactoring.

A useful review sentence: “This relationship is supported by configuration. Whether and how often it is used at runtime is unknown from the available data.”

The limit becomes a next step: supply references, record an execution, or check an assumption with the team. You leave with a question that can be answered.
